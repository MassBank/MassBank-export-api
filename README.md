# MassBank-export-api

A REST interface to export MassBank records to other formats.

This server was generated by the [OpenAPI Generator](https://openapi-generator.tech) project and uses
Spring Boot. It uses the RecordParserDefinition from the original
[MassBank project](https://github.com/MassBank/MassBank-web).

## Requirements

- Java 21
- Spring Boot 4.1
- maven
- PostgreSQL 17 with the Bingo PostgreSQL cartridge for shared API searches

## Configuration

### MassBank Data

This microservice is configured with environment variables. It requires a
directory with the [MassBank-data](https://github.com/MassBank/MassBank-data)
release. This directory needs to be configured in the environment variable
`MB_DATA_DIRECTORY`.

```bash
git clone https://github.com/MassBank/MassBank-data.git
export MB_DATA_DIRECTORY="$(realpath ./MassBank-data)"
```

### CORS

To configure CORS you can set the environment variable `CORS_ALLOWED_ORIGINS`.

```bash
export CORS_ALLOWED_ORIGINS=http://localhost:3000
```

### CONTEXT_PATH

The application serves the content at the given CONTEXT_PATH. If no CONTEXT_PATH
is given the application serves at root path http://localhost:8080/. To serve the
application at a different path set the environment variable CONTEXT_PATH,
e.g. `CONTEXT_PATH="/MassBank-export` and the server will listen on 
http://localhost:8080/MassBank-export.

### Using a Reverse Proxy

To make the Swagger UI work behind a reverse proxy one must configure
some X-Forward RequestHeader as descibed [here](https://springdoc.org/faq.html#_how_can_i_deploy_springdoc_openapi_starter_webmvc_ui_behind_a_reverse_proxy).
Here is an example for Apache:

```bash
RequestHeader set X-Forwarded-Prefix "/MassBank-export"
RequestHeader set X-Forwarded-Proto https
RequestHeader set X-Forwarded-Port 443
```

To make this work with a K8s nginx Ingress one needs to enable the property

```
use-forwarded-headers true
```

in the ingress-nginx-controller ConfigMap.
The application context path can be configured with the environment variable CONTEXT_PATH.
If not set / is used by default.

### PostgreSQL

Make sure to have a [PostgreSQL](https://www.postgresql.org) server installed and running on your system. The MassBank 
data will be stored there.

Both APIs use the same `DB_HOST`, `DB_PORT`, and `DB_NAME`. Defaults are
`localhost:5432`, database `massbank`, user `massbank`. Supply `DB_PASSWORD`
externally (for Kubernetes, use the existing `postgres-pw` Secret).

### Shared database ownership and migration

The import executable activates the `import` profile: Hibernate creates/updates
the canonical JPA tables and the importer fills them. The REST executable uses
`ddl-auto=validate` and never imports records at startup. Run the importer before
starting either API. Missing/empty input is rejected before deleting any records.
Imports replace the dataset and are not online/atomic swaps: schedule a maintenance
window and run only one importer at a time. Both APIs remain unready until all
files have imported successfully. Set `MB_DATA_VERSION` and `MB_DATA_COMMIT` to
identify the release in API metadata (defaults: `unknown`).

`shared-api.sql` adds read views and search indexes after JPA creates its tables.
Canonical records remain exclusively in those JPA tables in the same database.
The neutral-loss, name-search and metadata-statistics materialized views contain only derived
search/aggregate data. The importer refreshes them after every successful import
and before setting readiness; APIs never write them. Do not edit canonical tables
outside the importer and expect these projections to update automatically.
Bingo operates directly on the JPA `ch_smiles` column; the partial
index excludes empty/`N/A` structures. Other invalid structures follow the
installed Bingo configuration. PostgreSQL-specific DDL cannot be expressed as
JPA annotations.

The importer checks that Bingo is installed before modifying the dataset, marks
the database unready, and removes the previous cartridge index. It bulk-builds
that index only after all JPA records have been persisted, avoiding repeated
cartridge updates during collection persistence. Readiness is enabled only
after index creation, projection refresh and statistics collection succeed.

Covering expression indexes store computed atom counts and provide ordered
browse/formula results without per-request formula parsing. A partial covering
peak index avoids reading invalid peaks or fetching each matched heap tuple.
The neutral-loss projection preserves the original float arithmetic, peak IDs,
multiple precursors and raw-peak-count condition; its difference index replaces
millions of repeated JSON/regex operations per request.

For an already imported database, install this additive optimization without
reimporting records: stop concurrent imports, apply `src/main/resources/shared-api.sql`
with `psql -v ON_ERROR_STOP=1 --single-transaction`, then analyze the three projections
and vacuum/analyze `public."massbank-records"` and `public."massbank-peaks"`.
Initial projection creation reads the existing canonical dataset in that
transaction. Upgrade the Go API only after this migration succeeds. Keep the
Helm importer disabled for this software-only upgrade; explicitly enable it for
the next dataset import. Schema/index creation takes locks, so schedule a
maintenance window. The REST application remains schema-validation-only.

Regression checks on an imported test database:

```sh
psql -v ON_ERROR_STOP=1 -f deploy/test-shared-search.sql
mvn -Dtest=SharedDatabaseTest test
```

The SQL test rolls back all fixtures/schema changes and compares the complete
neutral-loss multiset and metadata aggregates against their original queries.

Provision a **fresh** database owned by the importer user; install Bingo into
that database with `/opt/bingo-postgres/init-scripts/000_bingo_install.sql` and set
`ALLOW_NON_UNIQUE_DEAROMATIZATION=1`. The cartridge's files must match the server's
PostgreSQL major version. The importer fails explicitly if Bingo is unavailable.
Installing Bingo into the old `massbank` database does not install it in another
database on the same server.

Point both services to the new database, set the Go API's `DB_SCHEMA=jpa`, and
disable the old dbtool Job/service. Do not copy its legacy tables into the shared
database. Keep the two old databases and old image/configuration references for
rollback. Import requires DDL/DML privileges; use a read-only role for API access
where possible. `MB_SHARED_DATABASE=false` supports export-only installations
without Bingo/read views; it is not suitable for the shared Go API.

The dedicated `shared-database-image.yml` workflow builds pushes on
`feat/shared-jpa-database` to
`quay.io/massbank/massbank-export-api:test-shared-jpa-<full-commit-SHA>`.
It does not overwrite release, `dev`, or `latest` tags.

### Isolated Kubernetes test

`deploy/shared-test-*.yaml` creates **additional** test services in `massbank-dev`,
using `massbank_shared_test` on `massbank-dev-postgres`. Existing deployments and
the old `massbank`/`records` databases are not changed. Provision the test database
and Bingo as described above before applying the manifests. They reference
immutable branch-image SHAs; update those references when testing newer commits.

From this repository, package the existing integration fixtures (677 records)
into a ConfigMap and run the importer image:

```sh
tar -czf /tmp/shared-fixtures.tar.gz -C src/test/resources MassBank-data-test
kubectl -n massbank-dev create configmap shared-jpa-fixtures \
  --from-file=/tmp/shared-fixtures.tar.gz --dry-run=client -o yaml | kubectl apply --server-side -f -
kubectl apply -f deploy/shared-test-import.yaml
kubectl -n massbank-dev wait --for=condition=complete job/shared-jpa-import --timeout=1800s
kubectl apply -f deploy/shared-test-services.yaml
kubectl -n massbank-dev rollout status deployment/shared-jpa-export
kubectl -n massbank-dev rollout status deployment/shared-jpa-api
rm /tmp/shared-fixtures.tar.gz
```

Port-forward `service/shared-jpa-api` and `service/shared-jpa-export` (port 8080)
to compare `/MassBank-api/records/count` with `/database/status`, retrieve the
same accession from `/MassBank-api/records/{accession}` and `/rawtext/{accession}`,
and exercise browse, formula, peak, neutral-loss and substructure filters.
With port forwards on localhost ports 18081 (API) and 18083 (export), run
`python3 deploy/check-shared-database.py` for these cross-service assertions.
The Go integration test also checks all imported records, read-only access and
the Bingo query plan. Delete only the named test Job before deliberately
rerunning it; it replaces the test dataset. To remove the test workloads, delete
the two manifests and `shared-jpa-fixtures`; the database is retained.


## Build and Run

Build the service with Maven:
```bash
mvn clean package
```

This build creates two executable jars:

- `target/massbank-export-api-rest-api.jar`
- `target/massbank-export-api-data-import.jar`

Import the MassBank records into the configured PostgreSQL database once before starting the REST API:
```bash
java -jar target/massbank-export-api-data-import.jar
```

Run the REST API:
```bash
java -jar target/massbank-export-api-rest-api.jar
```

## Run with Docker

### Build and Run

The file `docker-compose.yml` provides the config to build and run the postgres database and the MassBank-export-api
with docker. Copy `env.dist` file to `.env` file and configure to your needs. Then build and run with:

```bash
docker compose --profile import run --rm --build data-loader
docker compose up --build
```

This starts PostgreSQL and the REST API service. The importer is available as a separate on-demand service profile.

Run the importer profile when you want to (re)load data:

```bash
docker compose --profile import run --rm --build data-loader
```

Both services use one Docker image that contains two jars:

- `export-service` runs `/app-rest.jar`
- `data-loader` runs `/app-import.jar`

Then start or restart the REST API:

```bash
docker compose up --build export-service
```

### Use Pre-built Container

Pre-built Docker images are available from
[quay.io/massbank/massbank-export-api](https://quay.io/repository/massbank/massbank-export-api).
The fastest way to get things running after creating `.env` is:

```bash
docker compose --profile import run --rm data-loader
docker compose up
```

To run only the importer from the pre-built image:

```bash
docker compose --profile import run --rm data-loader
```

## Usage

For a description of how to use the api browse to the [Swagger UI](http://localhost:8080/swagger-ui/index.html).

The database status can be checked with:
```bash
curl http://localhost:8080/database/status
```

For readiness checks use:
```bash
curl -i http://localhost:8080/database/ready
```

`/database/ready` returns HTTP 200 when the database is reachable and contains active MassBank records, otherwise HTTP 503.

For example, to download all MassBank records in one zip file use the following command:

```bash
curl -X 'POST' \
  'http://localhost:8080/convert' \
  -H 'accept: application/zip' \
  -H 'Content-Type: application/json' \
  -d '{
  "format": "massbank"
}' --output records.zip
```

Or, for example, to get a record's raw text use the following command:

```bash
curl -X 'GET' \
  'http://localhost:8080/rawtext/MSBNK-IPB_Halle-PB001341' \
  -H 'accept: text/plain' \
  -H 'Content-Type: application/json'
```
